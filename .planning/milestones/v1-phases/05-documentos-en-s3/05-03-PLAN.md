## Phase Goal

**As a** job seeker, **I want to** upload my CV and cover letters and attach one of each to an application, **so that** I always know which documents I sent to each company.

This plan makes links trustworthy before any picker exists: the applications service accepts only links to real documents of the right type, PUT stops ignoring them (the Phase 2 hand-over), and the web form carries the loaded ids so a save never wipes them. It also proves rules 4 and 5 across both collections.

<objective>
API: a narrow `findTypes` lookup on the documents repository, injected into `createApplicationsService` (no service imports another service); link validation on create and update; `toEditableFields`, `EditableFields` and `updateEditable` include the two links; the stale Phase 2 test is rewritten. Web: `ApplicationFormValues` and its mappers carry both ids.

Purpose: D-12 and D-13 are what make DOC-03 safe; doing them first means 05-05 only adds UI.
Output: validated, editable links with real-Mongo tests; form values that round-trip the links.
</objective>

## Assumptions and decisions (explicit, for the user to review)

- **Lookup shape (RESEARCH Pattern 6).** The applications service receives a function, not the documents service or repository, so it cannot do anything with documents but read their types. A malformed id is «does not exist» (never an ObjectId constructor error, never a 500).
- **Messages (Claude's discretion).** «El documento no existe», «El documento no es un CV», «El documento no es una carta de presentación»; details in the `z.flattenError` shape, top message «Datos no válidos», like the global ZodError mapping.
- **Order on PUT.** Route: `parseObjectId` (404) → body schema (400) → service: links (400) → `updateEditable` (404 when unknown). Input is validated before existence, as the schema already is.
- **The Phase 2 test is rewritten** (`applications.update.test.ts` «keeps the document links, whether the body omits them, sends null or sends other values») because D-13 inverts it; its replacement asserts the D-13 behaviour with real documents. The comment above `toEditableFields` is replaced by one that states the links are editable and validated.
- **Web half of D-13 here, picker UI in 05-05.** Between this plan and 05-05 the form has no visible control for the links but already sends the loaded values back; nothing the user can do clears them.
- **Rule 5 check.** `applications.repository.ts` `deleteById` already touches only `applications`; the new test proves the documents survive and become deletable.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-05-17 | Tampering | links to unknown documents or of the wrong type | medium | mitigate | `validateDocumentLinks` in create and update before any write; tests for unknown, malformed and wrong-type ids |
| T-05-18 | Tampering | NoSQL injection through a link id | medium | mitigate | Contract types the ids as strings; `findTypes` queries only 24-hex ids converted to ObjectId inside `$in`; anything else is "does not exist" |
| T-05-19 | Tampering | silent loss of links on PUT | medium | mitigate | `toEditableFields` and `updateEditable` write the links; the web form always sends the loaded values (D-13); tests on both sides |
| T-05-SC | Tampering | npm installs | high | mitigate | No package installed |
