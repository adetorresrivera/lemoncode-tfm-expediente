## Planner choices (Claude's discretion, for the user to review)

- **Key name `idiomas`.** Spanish on purpose, like the existing «idioma» alias: G-03-2 showed that gemma4:e2b reads the English «language» as programming language, and in Spanish «idioma» only means a human language (programming languages are «lenguajes», the word the stack rule already uses). It is a model-facing key, not an API model: it never leaves the API, the contract keeps `tags` with group «language», and the web app does not change. The existing tests that no "language" reaches the model keep holding.
- **The model-facing tag enum keeps «idioma».** If the model ignores `idiomas` and still files a language as a tag, the guard keeps the common ones («Inglés B2»), so the common case cannot regress; only the prompt stops describing «idioma» under tags. That is also what makes the guard a real backstop for Ollama output.
- **`idiomas` goes first in the merge.** The array is trusted, so its entries are placed before the model's tags and the unchanged `normalizeTags` does the rest: a label in both places ends up once, in «language», with the `idiomas` spelling, and the languages are never cut by the 20-tag limit when the model returns 20 tags. Side effect: in the response array, language tags come before the others. The web groups chips by group, so nothing visible changes.
- **The mock stays as it is.** It is plan B for the demo and also the expected output of the route test (`toEqual(MOCK_OFFER_EXTRACTION)`). The raw schema accepts a missing `idiomas`, and «Inglés B2»/language passes the guard, so `LLM_PROVIDER=mock` still puts «Inglés B2» in «Idiomas». The new array is covered by the pipeline tests with fetch faked.
- **Approved prompt change (three line edits, all for the language rule).** (a) Remove the tags item that defines «idioma». (b) The label item keeps only the technology example, so it no longer suggests a language as a tag label. (c) Add a last rule that sends spoken languages to `idiomas`. Nothing else changes. The new fingerprint is computed above.
- **COVERAGE.md is unchanged.** Same endpoint, same providers, same capabilities (Ollama `/api/chat` `format`, OpenAI `response_format` json_schema with `strict: true`). Only the schema content grows by one array of strings with the same kind of bounds that `tags[].label` already uses. No capability decision changes, so no new matrix is needed.
- **Icon scope (live observation at planning time).** The 9 lucide icons in the 5 phase-03 surface files: 7 of them lack `strokeWidth={1.5}` (the ones listed in the review), while the `ChevronDown` in offer-panel and the `Sparkles` in tag-chip already have it, and ai-mark.tsx imports none. The icons in edit-states.tsx, native-select.tsx and the other phase 1/2 files are out of scope.
- **Task 2 touches 9 files.** That is above the 5-file guideline, but each edit is one attribute or one class token, plus the matching spec and test lines, so the task stays small. The orchestrator asked for at most 3 tasks.
