## Phase Goal

**As a** job seeker, **I want to** upload my CV and cover letters and attach one of each to an application, **so that** I always know which documents I sent to each company.

This gap plan closes G-05-4 (cosmetic, UAT test 4): in the upload dialog the native button «Seleccionar archivo» and its label «Ningún archivo seleccionado» look misaligned, and on the re-test of 2026-11-06 the user added that the native control «does not look like a button at all». The goal is therefore wider than alignment: the file-selector button must look like the app's own small outline button and sit centred beside the file name. Root cause of the misalignment (diagnosed in 05-UAT.md): the file input reuses the shared `Input` (`h-11`, `px-4`, `text-base`, no vertical padding); native file inputs flow their content from the top instead of centring it in a fixed height, and the `::file-selector-button` is `text-sm` with no height while the file-name text inherits `text-base`, so the two sit on different baselines near the top of the 44 px box.

<objective>
Style the native file-selector button of the upload dialog as the DS outline/sm button (border, fill, radius, shadow, hover, 14 px semibold label) and centre it beside the 16 px file-name text inside the 44 px «Archivo» control. Task 1 (tracer) does it red-first through a class assertion in the pod test and records the class list in the «Archivo» row of 05-UI-SPEC.md. Task 2 runs the full gate and makes the human check the condition for closing the gap, with a fallback inside this plan if the check fails. The upload dialog is the single component behind both modes (D-22), so the fix reaches /documents and the «Subir nuevo» picker of the application form (D-17) at once.

Purpose: the file control reads as a real button on one tidy line at 360 px and on desktop, so the demo of «Subir documento» looks finished.
Output: one className change, one new test, one amended UI-SPEC row, and a human check recorded in 05-UAT.md test 4.
</objective>

## Assumptions (explicit, for the user to review)

- User re-test 2026-11-06 (plan revision 2, confirmed by the user's dark-theme screenshot): «Seleccionar archivo» and «Ningún archivo seleccionado» both sit in the top third of the 44 px box, and the button has no border, fill or padding, so it reads as plain bold text; the user says it «does not look like a button at all». Out of scope: the browser's native title tooltip on hover («Ningún archivo seleccionado») is default behaviour that helps accessibility and is not suppressed. This widens G-05-4 and supersedes revision 1's 16 px choice, which was a framing error, not a user requirement. The plan now follows the DS contract on both sides. The button label takes the Label role, which 05-UI-SPEC Typography assigns to buttons: 14 px, `text-sm`, weight 600 (`font-semibold`). The file name keeps the input's Body role (16 px, `text-base`, from the shared Input). Both roles already exist, so the Typography section is unchanged and only the «Archivo» row records the classes. (Revision 1's rationale, that 16 px Body covered the button, was wrong: the Label row names buttons explicitly.)
- The button mirrors `Button variant="outline" size="sm"` (button.tsx) as `file:` utilities with DS tokens only: shape and spacing `file:inline-flex file:items-center file:h-8 file:px-3 file:mr-3 file:rounded-md`; border and fill `file:border file:border-border file:bg-background file:shadow-xs`; text `file:text-sm file:font-semibold file:text-foreground`; interaction `file:cursor-pointer file:transition-colors hover:file:bg-accent hover:file:text-accent-foreground`. `file:border-border` rather than `file:border-input` because `border-border` is the colour the outline variant actually resolves to (see `<interfaces>`); the input around it keeps its darker `border-input`, which stays the control's boundary. `gap`, `justify-center`, `whitespace-nowrap` and `shrink-0` are not carried over: the native button has a single text child and the engine already keeps its label on one line. The button's own focus ring is not carried over either, because keyboard focus lands on the input and the shared Input's `focus-visible` ring outlines the whole control.
- Layout arithmetic (tokens confirmed against the installed Tailwind 4.3.3, see `<interfaces>`): 44 px = 1 px border + 5 px (`py-1.25`) + 32 px button (`file:h-8`) + 5 px + 1 px border. The content row is exactly as tall as the button, so the button fills it whatever the engine's internal alignment. Chrome lays the control out from the top on a shared baseline, which is what left the pair near the top before. Inside the button, the 1 px border leaves 30 px and `file:items-center` centres the 20 px label line in it (5 px above and below). The file name's 24 px line shares the label's baseline and fits inside the 32 px row, so nothing overflows. A 16 px name beside a 14 px label on one baseline puts the name's glyphs about 1 px higher than the label's; that is within what the human check judges as centred, and F1-F3 cover it if not. The human check in Task 2 confirms the 32 px button height in devtools.

The button takes roughly 150-170 px with its margin, so the native control cuts the file name with its own ellipsis. 05-UI-SPEC's long-text row already accepts «the native file input shows its own truncated name». `w-full min-w-0` keeps the control inside the dialog, so there is no horizontal scroll.
