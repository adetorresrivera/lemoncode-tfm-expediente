## Assumptions and decisions (explicit, for the user to review)

- **Counter in the header through a `renderHeader` slot (D-27).** The count is pod data and a pod never pushes state to the scene from an effect, so the scene passes `renderHeader({ counter })` and the pod renders it first with its own polite counter element; the scene's header (eyebrow, h1, counter, upload container) is therefore exactly D-27 and UI-SPEC §4. This differs from `/applications`, whose counter sits under its header.
- **Refresh signal (D-27).** The scene keeps a `refresh` number, bumps it from `onUploaded`, and passes it as `refreshToken`; the list hook puts it in its key, so the reload keeps the previous rows with `aria-busy` (no skeleton flash).
- **Filter switch on upload (UI-SPEC §4).** When a filter is active and the uploaded type differs, the scene navigates to `?type=<uploaded>` with replace; otherwise only the refresh.
- **Delete is the response's truth.** `remove(id)` waits for the 204, then drops the row from the current result; it never refetches; a 409 or any failure rejects so the dialog shows its message.
- **Results region focus.** After a successful delete and after «Reintentar», focus moves to the `section aria-label="Resultados" tabIndex={-1}`, the only stable element left (UI-SPEC §4).
- **Edge DOC-05 «unclassified»** is reviewed in 05-02 (link/delete race accepted); the UI only displays the API's answer.
