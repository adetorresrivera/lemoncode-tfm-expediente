## Phase Goal

**As a** presenter, **I want to** have seeded data, a README and a responsive, accessible UI, **so that** the full demo runs in under 2 minutes on a clean machine.

This plan removes the API behaviours that can break a live demo on a fresh machine: a start that hangs or dies, a health probe without a deadline, a broken deploy hidden behind `200 text/html`, and unbounded request bodies.

<objective>
Bounded startup retry and S3 deadlines (D-16, Phase 1 findings), extension-aware SPA fallback with a loud missing `index.html` (D-18, 01 WR-08), a JSON body limit on the applications router and `.max()` on the unbounded strings in contracts (D-20, 02 WR-01), each finding flipped to `fixed`.

Purpose: DEMO-05 on a clean machine (cold start, slow dependencies).
Output: `startup.ts`, updated `main.ts`, `s3.ts`, `app.ts`, `applications.routes.ts`, contract bounds, tests, dispositions.
</objective>

## Assumptions and decisions (explicit, for the user to review)

- **Testable retry.** The loop lives in a small `startup.ts` helper with an injectable `sleep` and `log`, so it is unit-tested without waiting 20 s; `main.ts` only wires it.
- **Deadlines are parameters with defaults** (`pingS3(s3, bucket, timeoutMs = 2000)`, `ensureBucket(s3, bucket, timeoutMs = 5000)`), so tests use 300 ms and callers do not change.
- **Body limit scope.** Only the applications router gets the new 256 KiB cap (RESEARCH Pattern 5); the offers router already has one since Phase 3 (400 «La oferta es demasiado larga») and is not touched. Salary bounds, also suggested by the 02 WR-01 review text, are out of D-20 (strings and body limit) and are recorded as not applied in the disposition.
- **Finding ids (Pitfall 8).** The Phase 1 startup and `pingS3` findings came from the first review, whose ids WR-01 / WR-02 were reused by the second review; new rows WR-01a / WR-02a carry them with a Source note.
