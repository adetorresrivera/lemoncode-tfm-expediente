## Assumptions and decisions (explicit, for the user to review)

- **Where the screens live.** `common/components/` (not a pod; pods never import pods; the router imports them).
- **Forcing a route error in tests.** A separate test file mocks one scene module to throw (`vi.mock` is hoisted per file, so it cannot share `router.test.tsx`). For the 360 px guard, S10 is checked on the standalone `RootError` card, which shares its layout and classes with the in-shell `RouteError`.
- **jsdom has no layout.** The 360 px guard asserts the UI-SPEC §5 risk-point classes and the absence of oversized fixed widths. jsdom ignores media queries, so the 768 and 1280 px guards read classes instead: a class counts as active at a width when it has no prefix or its breakpoint is at or below that width (Tailwind `sm` 640, `md` 768, `lg` 1024, `xl` 1280). Content widths come from `layouts/app-layout.tsx`: `px-4` below `lg` (768 − 32 = 736), and at 1280 the `lg:w-64` sidebar plus `lg:px-8` (1280 − 256 − 64 = 960). Real `scrollWidth` and `clientWidth` are measured by the human pass of 06-17 and written as values per screen, viewport and theme into `06-UAT.md`, which the 06-17 UAT gate checks. 06-17 Task 3 fixes anything that pass finds.
- **Fix in place.** A view state or guard that fails is fixed with the smallest class or markup change in the owning component, the copy stays the approved Phase 2-5 copy, and each fixed file is listed in the SUMMARY. None is expected for the states (they were built in Phases 2-5); a few class fixes are possible for the guards.
