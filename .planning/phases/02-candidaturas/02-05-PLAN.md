## Phase Goal

**As a** job seeker, **I want to** create, find, review and move my applications through their states, **so that** I have one reliable record of every selection process.

This plan opens an application: the item endpoint, the card link and the full read-only detail.

<objective>
Serve one application by id with strict id handling (D-02) and let the user open it from a card into a detail that shows offer data, grouped tags, notes, the collapsible original text and the status history, with no rounds or documents sections (D-13, D-15, APP-09).

Purpose: the detail is where status changes and deletes happen (plan 02-06) and where the user lands after saving the form (plans 02-07, 02-09).
Output: `parseObjectId`, `GET /api/applications/:id` + test; route, scene and complete application-detail pod with its sections and states; card link.
</objective>

- A malformed id answers 404 NOT_FOUND, not 400 (RESEARCH Q4f: it cannot identify anything, and a single branch avoids an oracle).
- UI consideration "navigation — back link from detail" is **unresolved** in the UI-SPEC (RESEARCH Open Question 5): the back link goes to `/applications` and does not restore filters (UI-SPEC A-9). - The detail pod renders its own header (title, company, status) because it depends on loaded data; the scene renders the route-level frame only. `document.title` («{title} · Expediente», UI-SPEC A-14) is set by the container when the VM is loaded.
- The «Editar» action arrives with the edit route in plan 02-09 and the status selector and «Eliminar» in plan 02-06; this plan ships the read-only detail.
