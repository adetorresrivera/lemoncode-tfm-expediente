## Phase Goal

**As a** job seeker, **I want to** create, find, review and move my applications through their states, **so that** I have one reliable record of every selection process.

This plan lets the user move an application through its states from the detail and delete it safely.

<objective>
Implement the status rules atomically on the server (history entry per real change, appliedAt on the first move to enviada while empty, updatedAt on every modification — D-06, APP-10, APP-11, APP-13) and the optimistic, serialized, rollback-safe status selector in the detail (D-15). Then implement delete behind a confirmation dialog that never touches documents, returning the user to the list with a notice (D-14, D-15, APP-03).

Purpose: moving an application through its states is the heart of the tracker and a demo step («change status»).
Output: PATCH and DELETE endpoints + real-Mongo tests; status selector and delete dialog in the detail pod; alert-dialog primitive; arrival notice hook used by the list scene.
</objective>

## Assumptions (explicit, for the user to review)

- The optimistic update is hand-rolled (serialized with a busy ref, snapshot taken from the closure) instead of React `useOptimistic`, which let two PATCHes run concurrently in the research test (RESEARCH Q3).
- The status select uses `aria-disabled` and `aria-busy` while pending, never `disabled` (a disabled select drops keyboard focus; UI-SPEC §2).
- A same-status PATCH answers 200 with the unchanged application (idempotent), not an error (RESEARCH Q4d).
- The arrival notice is passed through router history state and cleared after reading, so a reload does not repeat it (UI-SPEC A-7). This plan wires it into the list scene for the delete flow; plan 02-10 wires it into the detail for create.
- Edge probes lifted here: APP-10 adjacency, APP-11 adjacency and ordering, APP-03 idempotency and concurrency.
- **Unresolved (flagged, per protocol):** the spec-less edge probe for APP-13 came back `unclassified`. It is left unresolved and surfaced here instead of being dropped. The updatedAt behaviour is still covered by explicit truths (creation in 02-01, PATCH here, PUT in 02-12); whether interview mutations bump updatedAt is owned by Phase 4 (ROADMAP cross-phase note).
