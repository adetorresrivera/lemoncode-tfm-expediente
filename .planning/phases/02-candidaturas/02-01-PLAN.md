## Phase Goal

**As a** job seeker, **I want to** create, find, review and move my applications through their states, **so that** I have one reliable record of every selection process.

This plan is the phase tracer: the thinnest production-quality path from Mongo through the applications API to the list screen, then the four list states on top of it. Later plans widen each layer (tags, filters, detail, status, delete, form) without changing this architecture.

<objective>
Prove the CRUD architecture end to end on one path: `POST /api/applications` and `GET /api/applications` through repository → service → mapper → Hono sub-app on real Mongo (D-01, D-02, D-06, D-11), and `/applications` fetching that list through the course pod (D-12). Then give the list its loading, error-with-retry, empty and populated states, the counter and the Phase 1 layout carry-over (APP-05, UI-SPEC C-1, C-2).

Purpose: a dead end in the API layering, the db injection, the test database or the keyed-result hook surfaces after one commit, not after nine plans.
Output: applications repository/service/mapper/routes + require-json + test DB helper + integration test; list pod hook, states and tests; mock-fetch helper; scene and layout carry-over.
</objective>

## Assumptions (explicit, for the user to review)

- D-11 is honoured literally: the API tests use the database named exactly `tfm_test` and clean it before each test. RESEARCH (Decision Risk 2) showed that parallel test files sharing one database race; instead of renaming the database per file, `apps/api/vitest.config.ts` sets `fileParallelism: false` (API files run one after another; the suite is about 10 s). Reversible: switching to `tfm_test_<suffix>` later is a one-line change in the helper.
- In this plan `ApplicationDoc.tags` stores the contract `Tag` shape; plan 02-02 adds the normalized `key` per tag. No UI can create applications before plan 02-07, so no stored document lacks the key outside the cleaned test database.
- `GET /api/applications` ignores query parameters until plan 02-03 adds the filters; this plan proves the path, not the query.
- The empty-state call to action «Añadir la primera candidatura» and the header «Añadir candidatura» link to `/applications/new`, which only exists from plan 02-07, so they land there (typed router links to a missing route do not compile).
- The counter is rendered by the list pod as the first line of its output (it depends on pod data); the scene keeps eyebrow and `h1`. Visually it sits under the heading.
- Spec-less edge probes lifted here: APP-01 idempotency and concurrency, APP-11 empty (POST part), APP-10 empty, APP-05 empty, ordering and idempotency. The remaining APP-05 probes (adjacency, concurrency) depend on filters and are lifted in plan 02-03.
- Canon security items (NoSQL injection, mass assignment, CSRF by simple request) are handled in the threat model below and by /gsd-secure-phase, not minted as prohibitions.
