## Phase Goal

**As a** job seeker, **I want to** create, find, review and move my applications through their states, **so that** I have one reliable record of every selection process.

This plan is the phase tracer: the thinnest production-quality path from Mongo through the applications API to the list screen. Plan 02-02 expands it on the web side with the four list states; later plans widen each layer (tags, filters, detail, status, delete, form) without changing this architecture.

<objective>
Prove the CRUD architecture end to end on one path: `POST /api/applications` and `GET /api/applications` through repository → service → mapper → Hono sub-app on real Mongo (D-01, D-02, D-06, D-11), and `/applications` fetching that list through the course pod (D-12). The list's loading, error-with-retry, empty and populated states, the counter and the layout carry-over follow in plan 02-02.

Purpose: a dead end in the API layering, the db injection, the test database or the keyed-result hook surfaces after one commit, not after twelve plans.
Output: applications repository/service/mapper/routes + require-json + test DB helper + integration test; list pod hook wired to the API with minimal states and tests; mock-fetch helper.
</objective>
