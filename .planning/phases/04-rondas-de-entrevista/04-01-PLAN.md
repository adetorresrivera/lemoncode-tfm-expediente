## Phase Goal

**As a** job seeker, **I want to** log the interview rounds of an application, **so that** its process history and status stay in sync without extra bookkeeping.

This plan is the phase tracer: the thinnest production-quality path from «Añadir ronda» in the detail, through a dialog with a TanStack form, the detail hook and `POST /api/applications/:id/interviews`, to one atomic Mongo update that also applies rule 3, and back into the view (rounds, badge and history replaced by the response). Later plans widen it without changing this architecture: date, mode, outcome and notes controls plus the full round row and ordering (04-02), edit and delete (04-03), the status select waiting for round changes and the phase gate (04-04).

<objective>
Wire one path end to end: `InterviewsSection` («Añadir ronda», polite region, list) → dialog form (`useInterviewForm`, contracts schema through the pod mapper) → `interviewActions.add` in `useApplicationDetail` (shared busy guard) → `createInterview` → `POST /:id/interviews` (`parseObjectId`, `interviewInputSchema`) → `service.addInterview` (id, field-by-field element, `INTERVIEW_STATUS_RULE`) → `repository.addInterview` (one pipeline `findOneAndUpdate`). Task 1 is the tracer; Task 2 covers the limits, the failures and the concurrency of the same path.

Purpose: a dead end in the atomic update, the trigger-less dialog focus or the busy guard shows up after one commit, not after four plans.
Output: round creation endpoint with real-Mongo tests; Dialog primitive; enum labels; the rounds section with the add dialog in the detail pod and its tests.
</objective>

## Assumptions and decisions (explicit, for the user to review)

- **Rule 3 location (RESEARCH open question 2, resolved there with this reading).** D-04 says the rule lives in `applications.service.ts`; D-05 requires one atomic write. Reading recorded here: the service owns the rule as `INTERVIEW_STATUS_RULE = { from: "enviada", to: "en_entrevistas" }` and passes it to `repository.addInterview`, whose pipeline evaluates it in the same `findOneAndUpdate`. The repository holds no status literal of its own.
- **Create uses a pipeline update instead of the `$push` operator D-05 names (deviation, D-05 intent kept).** D-05 asks for an atomic create with `findOneAndUpdate` and `returnDocument: "after"`, and names `$push` plus a `$set` of status and a `$push` of history "when it applies". A classic update document cannot read the stored rounds (max + 1, D-03) or the stored status (rule 3 only from `enviada`, D-04) inside the same write, so the `$push` form needs a read before the write and two concurrent creates could get the same number or two history entries. The pipeline form appends exactly one element with `$concatArrays` (what `$push` would do) and decides status and history with `$cond` on the input document, in one `findOneAndUpdate` with `returnDocument: "after"` (RESEARCH Pattern 1, executed against Mongo). Atomicity, the single write and the return shape of D-05 are unchanged; edit (`$set` with `arrayFilters`) and delete (`$pull`) in 04-03 use the operators D-05 names.
- **APP-13 is claimed only for its rounds part** (CONTEXT.md phase boundary: «la parte de rondas de APP-13 (`updatedAt`)»): creating a round sets `updatedAt`; edit and delete do so in 04-03; the rest of APP-13 shipped in Phase 2.
- **Focus return (RESEARCH Pitfall 1).** Radix restores focus only to a `Trigger`; this dialog is controlled and trigger-less, so `onCloseAutoFocus` calls `preventDefault()` and focuses the opener stored from `event.currentTarget` on click (RESEARCH Pattern 4, verified). This replaces the UI-SPEC sentence «Radix returns focus…» with the mechanism that delivers it.
- **Existing tests that change in Task 1 (RESEARCH Pitfall 6).** In `application-detail.test.tsx`: the strict view-model test at ~L72 gains `interviews: []` and `newInterviewValues`; the Phase 2 test at ~L535 that asserts no rounds heading or button keeps only its documents half under a new name; the polite-region count at ~L1079 goes from 2 to 3 (header slot, notice line, rounds region); the three direct renders of `ApplicationDetailComponent` (~L323, ~L566, ~L623) pass an idle `interviewActions`. Same commit as the section, because the pre-commit hook runs the suite.
- **Thin dialog in this plan.** It shows Tipo and Ronda; `mode: "online"` and `outcome: "pendiente"` travel as form defaults (D-19) and get their toggle groups in 04-02 together with Fecha y hora and Notas. `InterviewFormValues` and the mapper already carry every field, so 04-02 adds controls without changing the model. The list shows each round as «Ronda N · Tipo» in API order; 04-02 adds the meta row, notes and the D-07 order.
- **No component imports the mapper.** The add defaults come in the view model (`newInterviewValues`, built by the mapper in the hook); the dialog's form instance is UI state created by `useInterviewForm` (pod hooks file) inside the dialog content, so every opening starts fresh (RESEARCH Pattern 5).
- **Dialog footer order.** UI-SPEC asks for keyboard order «Guardar ronda» → «Descartar cambios» and «Guardar ronda» on top on mobile, which a reversed column cannot give with that DOM order; the dialog form uses `flex flex-col gap-2 sm:flex-row sm:justify-end`, the same as the application form. `DialogFooter` in `ui/dialog.tsx` keeps the UI-SPEC class for other uses.
- **`dialog.tsx` is hand-written** on the unified `radix-ui` import, modelled on `alert-dialog.tsx`, with the classes of UI-SPEC «Dialog primitive adaptation» (RESEARCH: the shadcn CLI needs the network registry and its output is adapted anyway). No dependency is added.
- **scheduledAt normalization.** The service stores `new Date(value).toISOString()` (RESEARCH A2): same instant, always millisecond precision.
- **Round cap (edge INT-02 precision, planner decision).** max + 1 is capped at `Number.MAX_SAFE_INTEGER` on the API and in the client prefill, so an automatic number never fails the contract; repeated numbers are allowed (D-07).
- **Branch.** CLAUDE.md asks for `phase/04-rondas-entrevista`; branch handling stays with `/gsd-execute-phase` (STATE blocker on the branching config).
- Spec-less edge probes lifted here: INT-01 boundary and precision (API part), INT-02 boundary and precision, INT-04 boundary and precision. The INT-03 edges are in 04-03 and the INT-05 edges in 04-02.
