## Phase Goal

**As a** job seeker, **I want to** log the interview rounds of an application, **so that** its process history and status stay in sync without extra bookkeeping.

This plan lets the user correct and remove rounds from the detail (INT-03): each task is one full slice, API and web together.

<objective>
Task 1: `PUT /:id/interviews/:interviewId` (per-key `$set` with `arrayFilters`) and the edit mode of the existing dialog, opened from a Pencil button on each row. Task 2: `DELETE /:id/interviews/:interviewId` (`$pull`, 200 with the application) and a confirmation `AlertDialog` opened from a Trash2 button, with focus moved to «Añadir ronda» after the delete.

Purpose: a mistyped or cancelled round can be fixed in seconds, and the status never moves as a side effect.
Output: two endpoints with real-Mongo tests; edit mode, row actions and the delete dialog in the detail pod with tests.
</objective>

## Assumptions and decisions (explicit, for the user to review)

- **PUT with an empty «Ronda» field (RESEARCH open question 1).** Respecting D-03 («editable en PUT»), D-05 (edit is a `$set` with `arrayFilters`, no pipeline) and D-09 (the client computes the suggested number from the view model): the edit dialog never sends an empty round. When the field is emptied the hook sends the highest round of the other rounds + 1 (capped like the add prefill), so the always-visible hint «Si lo vacías, se asigna la siguiente.» is true in both modes. A PUT without `round` from another client keeps the stored round (the key is left out of the `$set`). The research suggestion «send the current round» was not taken because it would make that hint false in edit mode.
- **`:interviewId` is a plain string** compared by equality (filter, `arrayFilters`, `$pull`); it is not passed to `parseObjectId`, whose message names the application (RESEARCH Pattern 3). A malformed or unknown round id on an existing application answers «Ronda no encontrada».
- **Focus after a delete.** The deleted row's buttons are gone, so after success focus moves to the section's «Añadir ronda» (UI-SPEC «Focus after a successful delete», the one programmatic focus move of the phase); after a cancel it returns to the delete button that opened the dialog, through the same `onCloseAutoFocus` mechanism as the round dialog, falling back to «Añadir ronda» when the opener is no longer connected.
- **«Eliminando…» state** comes from `actions.busy` (nothing else can run while the modal is open); the failure flag is local to the section.
- Spec-less edge probes lifted here: INT-03 boundary, precision, idempotency and concurrency.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-10 | Tampering | `:interviewId` path parameter | medium | mitigate | Always a string compared by equality in the filter, `arrayFilters` and `$pull`; never turned into an operator or a key; the body is never spread into the update |
| T-04-11 | Tampering | PUT body → element id (mass assignment) | medium | mitigate | Per-key `$set` of type, scheduledAt, mode, notes, outcome and round only; the id key is never written; test that a body id is ignored |
| T-04-12 | Tampering | resurrecting a deleted round | medium | mitigate | Filter requires the element (`"interviews.id"`), no insert-on-miss option; DELETE → PUT 404 test and concurrent PUT/DELETE test |
| T-04-13 | Tampering | accidental deletion | low | mitigate | AlertDialog confirmation with initial focus on «Conservar ronda»; one DELETE in flight (busy guard) |
| T-04-14 | Information disclosure | distinct 404 messages for application and round | low | accept | Single-user local app without accounts (`ownerId` null); the two messages only tell the UI which resource is missing |
